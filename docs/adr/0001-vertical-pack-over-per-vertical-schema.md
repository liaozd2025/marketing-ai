# ADR-0001: 垂类适配用「核心实体 + 垂类包配置」，不用独立 schema 或全可配置实体引擎

日期：2026-07-29 · 状态：已接受

## 背景

平台要同时服务美业/大健康与电商/品牌零售两个垂类，两者的知识库内容差异大（服务项目/卡项 vs SKU/卖点），且未来可能扩展更多垂类。备选方案：每垂类独立表结构（零复用）、EAV 全可配置实体引擎（MVP 过度设计）、固定核心实体 + 垂类配置。

## 决策

六个固定核心实体：品牌档案、Offering（可售卖物统一抽象）、素材、客群、活动、会员分层。垂类差异全部收敛进**垂类包**配置：Offering 字段模板、场景词表、违禁词表、Skill 预设。

## 后果

- 加新垂类 = 加一份垂类包配置，不做数据库迁移。
- Offering 抽象必须同时容纳美业与电商：Phase 1 内用电商字段模板做纸面试填校验。
- 垂类包是配置数据而非代码分支——Skill 实现不得出现 `if (vertical === 'beauty')` 式硬编码。

## 2026-07-30 电商纸面校验补充

结论为**有条件成立**，完整证据见
[电商 / 品牌零售垂类包纸面校验](../research/2026-07-30-ecommerce-vertical-pack-validation.md)。
不为电商新增独立 schema，但收紧以下边界：

- 电商中的一个 Offering 表示一个可独立定价、售卖和履约的 SKU / 商品变体，
  不是包含多个规格组合的商品族。同一商品族的多个 SKU 是多个 Offering。
- Offering 保存稳定商品事实，以及人工确认过的价格、库存和履约快照。限时促销
  归活动；图片与视频归素材；实时价格、多仓库存、订单和履约状态的事实来源在
  知识库之外。
- `fieldValues` 的 JSONB 存储边界继续成立，但“能保存 JSON”不等于垂类字段
  契约已经完整。电商运行态接入前，字段模板需要补足可重复规格、时间类型、
  条件 / 跨字段校验和动态事实的新鲜度语义。

出现以下情况时重新评估本决策，而不是继续把结构压入 textarea：

1. 商品族及其变体需要强引用完整性、跨 Offering 原子更新或高频结构化查询。
2. 价格、库存和配送承诺需要由外部系统实时同步并直接参与自动发布。
3. 同一商家需要同时启用多个垂类包，且同名字段的语义或版本无法由商家级
   `vertical_pack_id` 唯一解释。
